# Workflow

## Repository map

| Path | Contents |
| --- | --- |
| `main.go` | Server startup, healthcheck flag, graceful shutdown, session cleanup |
| `static_prod.go` / `static_dev.go` | `go:embed` of `web/dist`; `dev` tag disables assets for tests |
| `internal/api/` | Gin router, auth, middleware, task/calendar/stats handlers, static serving |
| `internal/auth/` | Password verification, session tokens, cookie rules |
| `internal/config/` | Environment configuration |
| `internal/store/` | SQLite access, migrations, tasks, calendar/stats aggregates |
| `web/src/` | React SPA: pages, components, hooks, API client, styles, tests |
| `web/public/` | Manifest, icons, service worker, registration script |
| `scripts/` | Bun dev/build/test/start orchestration |
| `architecture.md` | Authoritative design and operations notes |
| `README.md` | User-facing run/deploy guide |

Read `architecture.md` before changing behavior, and update it when the change affects architecture, API, data model, configuration, or the performance profile.

## Before you start

- Read the files you will change and the nearest tests.
- Check `git status`; do not overwrite unrelated user work.
- For UI work, read `.agent/20-frontend.md` and plan a browser check.
- For Go work, pick the relevant skill from `.agent/10-go.md`.

## Verification

Run the smallest set that proves the change, then the full set before finishing:

```bash
bun run typecheck
bun run test          # frontend tests, then Go tests
go vet -tags dev ./...
bun run build         # when changing build output, assets, or embedding
```

- Frontend tests use `bun test` and live beside the code as `*.test.ts`.
- Go tests use `-tags dev` so they run without `web/dist`.
- Format changed Go files with `gofmt -w`.

## Change rules

- Keep the design small: no extra runtime process, database, queue, or frontend framework.
- All SQL stays in `internal/store`; HTTP concerns stay in `internal/api`.
- Reuse existing helpers, hooks, and CSS variables before adding new abstractions.
- Update docs in the same change:
  - API/route changes → `architecture.md` §5
  - Data model or rules → `architecture.md` §4 + a numbered migration
  - Configuration → `architecture.md` §6 + `.env.example`
  - Performance-relevant changes → `architecture.md` §13
- Add or update tests for every behavior change, including error paths.
- If a requirement changes, follow the protocol in `.agent/40-requirements.md`.

## Dependencies and versions

- Use the versions already pinned in `go.mod`, `bun.lock`, `Dockerfile`, and CI.
- Prefer the standard library and existing dependencies over new packages.
- A new frontend dependency must justify its bundle cost and have a Bun-compatible install path.
- A new Go dependency must be maintained, license-compatible, and work with `CGO_ENABLED=0`.

## Tooling rules

- **Bun only:** `bun install`, `bun run <script>`, `bunx <tool>`, `bun test`, `bun build`.
- Never run `npm`, `npx`, `yarn`, `pnpm`, `node <script>`, Jest, Vitest, webpack, or Vite.
- If a tool only ships a Node entrypoint, run it with `bunx` / `bun <file>` or choose a Bun-native alternative; do not add a Node toolchain to the repo.
- Treat `bun.lock` as the only lockfile. Do not introduce `package-lock.json`, `yarn.lock`, or `pnpm-lock.yaml`.

## Never edit or commit

- `web/dist/`, `bin/` — generated by the build.
- `data/`, `*.db`, `*.db-shm`, `*.db-wal` — local data.
- `.env`, `.env.local` — secrets.
- Backups or database copies.
